# 歌词获取链路（移植说明）

这份文档描述一个**从系统媒体会话取当前播放曲目 → 多源搜索歌词 → 匹配打分 →
解析 → 缓存 → 渲染**的完整实现。它是从 Glance（Windows 桌面磁贴应用）的实现里
抽出来的，但**除「数据来源」一节与 Windows SMTC 绑定外，其余部分与平台无关**。

面向读者：要在另一个项目里复刻这套逻辑的开发者 / agent。文中所有阈值、正则、
权重都是从线上实现里原样摘出来的，可直接照抄。

---

## 0. 总览

```
┌──────────────────────────────────────────────────────────────────┐
│ 1. 数据来源（平台相关）                                            │
│    系统媒体会话 → {title, artist, duration, position, status}      │
└────────────────────────┬─────────────────────────────────────────┘
                         │ 每 100ms 轮询一次
                         ▼
┌──────────────────────────────────────────────────────────────────┐
│ 2. 换歌判定                                                       │
│    key = "title|artist|时长秒"  变了才走后续流程                    │
└────────────────────────┬─────────────────────────────────────────┘
                         ▼
┌──────────────────────────────────────────────────────────────────┐
│ 3. 本地缓存                                                       │
│    命中 → 直接渲染；未命中 → 搜索                                  │
└────────────────────────┬─────────────────────────────────────────┘
                         ▼
┌──────────────────────────────────────────────────────────────────┐
│ 4. 搜索编排（多源 + 多变体 + 兜底，顺序尝试，先成功者胜）            │
│    源 A 网易云：  变体 × (标题+歌手) → 只搜歌手(兜底)               │
│    源 B LRCLIB：  api/get × 变体 → api/search(兜底)                │
└────────────────────────┬─────────────────────────────────────────┘
                         ▼
┌──────────────────────────────────────────────────────────────────┐
│ 5. 匹配打分（pickSong）                                            │
│    歌手 / 时长 / 标题 / 垃圾词 / 搜索排序 → 总分 ≥ 60 才采用        │
└────────────────────────┬─────────────────────────────────────────┘
                         ▼
┌──────────────────────────────────────────────────────────────────┐
│ 6. LRC 解析（+ 翻译合并）→ 写缓存 → 渲染                            │
└──────────────────────────────────────────────────────────────────┘
```

**核心设计取舍**：宁可显示"没找到"，也不要贴一首**别的歌**的歌词。所有阈值都
服务于这一点——这也是为什么匹配环节有一个明确的分数门槛，而不是"取第一个结果"。

## 1. 数据来源（与平台绑定，需要替换）

Windows 上从 **SMTC**（`GlobalSystemMediaTransportControlsSession`）读：

```dart
// 字段清单（本实现实际用到的）
{
  'available': bool,     // 是否有媒体在播
  'title':     String,
  'artist':    String,
  'duration':  int,      // 毫秒
  'position':  int,      // 毫秒，播放器上一次上报的位置
  'positionAge': int,    // 从"上报位置"到"我们采样"之间过了多久（毫秒）
  'status':    int,      // 4 = playing
  'artId':     int,      // 封面标识（可选）
}
```

**别的平台替换要点**：

| 平台 | 取法 | 注意 |
|---|---|---|
| Windows | SMTC | `get_sessions()` 而非 `get_current_session()`——浏览器（Edge）会抢走"当前会话"，实测抓到的是 B 站视频标题 |
| macOS | `MediaRemote` / `osascript` 读 Spotify/Apple Music | 需要辅助功能权限 |
| Linux | MPRIS（`org.mpris.MediaPlayer2`）| 各播放器实现完整度不一 |
| Android | `MediaSessionManager.getActiveSessions()` | 需要 NotificationListener 权限 |
| iOS | `MPNowPlayingInfoCenter` | 只在自己 App 内可用 |

**两个必须处理的现实问题**：

1. **标题/歌手可能被翻译或罗马字化**。实测案例：Spotify 上报
   `title='Golden Number' artist='Iyowa'`，而曲库里存的是
   `歌名='黄金数' 歌手='いよわ'`——**两头都跨了文字**。匹配算法必须为此兜底
   （见 §5）。
2. **切歌间隙 `available` 会短暂变 false**。此时**不要**清空画面，否则会闪空白。
   本实现的做法：连续 ~1 秒（`_idleGrace`）没有有效信号才判定停播。

## 2. 换歌判定

```dart
final key = '$title|$artist|${(durationMs / 1000).round()}';
if (key != _trackKey) {
  _trackKey = key;
  // 触发加载。注意：不清空旧歌词，保留到新歌词到位，避免空白闪屏
  _loadLyrics(title, artist, durationMs, key);
}
```

**为什么 key 里带时长**：同一首歌的**现场版 / 录音室版 / 不同 remix** 标题歌手
全一样，靠时长区分。取整到秒即可（各平台同版本时长差异通常 <1 秒）。

**为什么 duration 取整而不是原值**：不同平台对同一音轨的上报值可能差几十毫秒，
用原值会导致"明明没换歌却判定换了"。

## 3. 本地缓存

- **键**：就是上面的 `key`（`标题|歌手|时长秒`）
- **值**：`[{t: 毫秒, s: 原文, tr: 翻译}, ...]`（可直接序列化）
- **命中**：直接渲染，**不联网**
- **写入**：搜索成功后才写；搜不到**不写负缓存**（避免网络恢复后仍显示"没找到"）

**存储介质怎么选都行**（本实现用应用自己的键值存储）。注意一点：**别把整份
歌词塞进主配置文件**——本项目的配置以前是单文件，实测 99KB 里有 98% 是歌词全文。
歌词应该单独存放（独立文件 / KV 表 / SQLite）。

## 4. 搜索源

### 4.1 网易云（非官方 API）

**搜索**：

```
GET https://music.163.com/api/search/get?s=<URL编码的查询>&type=1&limit=<N>
Headers:
  Referer: https://music.163.com/
  User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
```

响应结构：

```json
{ "result": { "songs": [
  { "id": 1825071525,
    "name": "黄金数",
    "artists": [{ "name": "いよわ" }],
    "duration": 187924 }
] } }
```

**取歌词**：

```
GET https://music.163.com/api/song/lyric?id=<songId>&lv=1&kv=1&tv=-1
```

- `lrc.lyric` = 原文 LRC
- `tlyric.lyric` = 翻译 LRC（可能为空，时间戳与原文不一定完全对齐）

**要点**：
- 这是**非官方接口**，必须带 `Referer` 和正常 UA，不带容易被限流。
- `limit` 建议：标题+歌手组合搜 10 条；**只搜歌手时给 30 条**（下面 §5 会解释
  为什么要那么宽）。 

### 4.2 LRCLIB

```
GET https://lrclib.net/api/get?track_name=<>&artist_name=<>&duration=<秒>
GET https://lrclib.net/api/search?track_name=<>&artist_name=<>
```

- **只有 `syncedLyrics` 字段可用**（`plainLyrics` 没有时间轴，无法逐行高亮）。
- `api/get` 是精确匹配，命中就返回单条；`api/search` 是模糊匹配，返回数组。
- **国内直连会 503，需要代理**。所以它只适合当**兜底**，不能当唯一来源。

## 5. 搜索编排（这是整套逻辑里最需要照抄的部分）

### 5.1 标题变体

搜索引擎对"同一个标题的不同写法"返回结果差异很大，所以要**逐个变体尝试**
（顺序即优先级）：

```dart
List<String> titleVariants(String title) {
  // 按优先级 push（原样 → 去括号 → 括号内容 → 繁转简 → 繁转简去括号 →
  //             纯拉丁字符子串 → 纯 CJK 字符子串）
  // 去重键用**原始字符串**，不能用归一化后的——归一化会剥掉括号内容，
  // 「X (Y)」和「X」会被误判成同一个变体，而它们对搜索引擎是两个完全
  // 不同的查询，恰恰是要分开试的。
}
```

举例，`"なんでもないや (movie ver.)"` 会生成：

```
"なんでもないや (movie ver.)"   ← 原样
"なんでもないや"                 ← 去括号
"movie ver."                    ← 括号内容
```

`"Golden Number（English Cover）"` 会额外得到 `"Golden Number"` 这类变体。

### 5.2 编排顺序

**源内部**（以网易云为例）：

```
1. 对每个标题变体：搜「变体 + 歌手」，limit=10
2. 兜底：只搜「歌手」，limit=30
```

**为什么"只搜歌手"是必要的兜底**：歌名被翻译成另一门语言时，无论怎么变体都
搜不到——但"这个歌手的歌"里一定有它，用**时长**就能挑出来（见 §6）。

**源之间**（`source=auto` 时）：

```
网易云（全部变体 + 兜底） → 都没结果才轮到 → LRCLIB（api/get + api/search）
```

**顺序尝试的实现**：

```dart
Future<T?> _trySeq(List<Future<T?> Function()> attempts, int i) async {
  if (i >= attempts.length) return null;
  T? r;
  try { r = await attempts[i](); } catch (_) { r = null; }
  if (r != null) return r;          // 空结果也算失败，继续下一个
  return _trySeq(attempts, i + 1);
}
```

**要点**：
- **逐个**尝试，不要并发 —— 并发会同时打多个接口，既浪费请求也容易触发限流，
  而且顺序本身就是优先级（先试最可能命中的路径）。
- 任一步抛异常都算失败，继续下一个，不让单点故障毁掉整条链。

## 6. 匹配打分（pickSong）

搜索结果**不能取第一个**——搜索引擎的排序对跨语言场景不可靠。要对每条候选打分，
**总分 ≥ 60 才采用**，否则返回 null（显示"没找到"）。

| 信号 | 判定 | 分值 |
|---|---|---|
| **歌手** | 归一化后一方包含另一方 | **+60** |
| | 明确对不上 | **−15** |
| | 任一方为空 | 0（不表态） |
| **时长** | 差值 ≤ 3 秒 | **+80** |
| | 差值 > 3 秒 | `−min(50, 超出秒数 × 3)`（渐进扣分） |
| **标题** | 完全相等 | +40 |
| | 一方包含另一方 | +25 |
| | 相似度 ≥ 0.3 | `+(相似度 × 30)` 取整 |
| | 对不上 | 0（**不扣分**——繁简/异体/翻译都会让字面对不上） |
| **垃圾词** | 候选标题含 `伴奏/instrumental/remix/dj版/纯享/翻自/cover/live/现场/demo/加速/减速/钢琴版/吉他版`，而目标标题**不含** | **−70** |
| **搜索排名** | 第 i 条 | `+max(0, 10 − i×2)` |

### 为什么是这套权重（都是踩出来的）

**时长权重最高（+80）不是随意定的**。在"歌名被翻译、歌手名被罗马字化"的场景里，
时长是**唯一还靠谱**的信号：同一首歌各平台差异通常 <1 秒，不同歌撞上同一时长的
概率很低。把它提到 80，一个时长吻合的候选**即使歌手名完全对不上**也能独立通过门槛。

**歌手不匹配只扣 15，不扣 40**。歌手名**跨文字**对不上是常态而非异常：

```
Spotify 给    artist='Iyowa'
曲库里存的     artist='いよわ'      ← 同一个人
```

两者做字符串包含判定必然失败。早期版本扣 −40，结果正确的候选只拿到 14 分被判
"没找到"（真实案例：网易云确实有这首歌，就是被打分挡在门外的）。改成 −15 后
同一批数据下目标得 69 分命中，而**时长差 10~12 秒的近似候选仍在 −30 以下被拒**
——没有误选。

**标题匹配不扣分**。繁简、异体字、翻译名、罗马字都会让字面完全对不上，但
"对不上"不等于"不是它"。真正的判断交给时长。

**阈值 60 的由来**：一个"歌手对得上但标题完全对不上"的候选拿 60+ 排序分就能过；
而"歌手对不上、时长也不匹配"的候选即使标题命中也到不了（+40 −15 = 25）。

### 一个被验证过的取舍

在"宁可漏，不可错"和"宁可错，不可漏"之间，这里选**前者**：门槛不到就显示
"没找到"，让用户可以手动去别处找。贴错歌词（别人的词配你的歌）比没有歌词
更让人恼火，而且用户很难判断"是没找到还是贴错了"。

## 7. 归一化与相似度

所有标题/歌手比对**必须**走同一个归一化入口（否则规则会各处不一致）：

```dart
String norm(String s) => toSimplified(s)        // 繁 → 简（逐字查表）
    .fullwidthToHalfwidth()                     // 全角 → 半角
    .toLowerCase()                              // 大小写
    .replaceAll(r'[（(\[].*?[)）\]]', '')        // 剥掉括号内容
    .replaceAll(r"""[\s\-_·,，.。!！?？'"“”‘’]""", '');  // 去掉空白与标点
```

**繁简映射表**：手工维护的常用字对（几百对），**不求全**——错字漏字的代价是
"该加的分没加上"，不会把正确结果挡在门外，所以可以放心用有限表。

**相似度**：二元组（bigram）Dice 系数。

```
sim(a, b) = 2 × |bigrams(a) ∩ bigrams(b)| / (|bigrams(a)| + |bigrams(b)|)
```

- 长度 <2 的字符串退化成相等判定（否则 bigram 为空会除零）
- 选 Dice 而不是编辑距离：对**词序不敏感**（"Number Golden" 和 "Golden Number"
  相似度仍然很高），且 O(n) 一次遍历

## 8. LRC 解析

### 8.1 时间戳正则

```dart
RegExp(r'\[(\d{1,3}):(\d{1,2})(?:[.:](\d{1,3}))?\]')
```

覆盖现实中的各种写法：`[mm:ss.xx]`、`[mm:ss:xx]`（少数源用冒号）、`[mm:ss]`。

**小数位数必须按长度判**：

```dart
final v = int.parse(frac);
ms = frac.length == 1 ? v * 100 : (frac.length == 2 ? v * 10 : v);
```

- 1 位 → 十分秒（`[00:01.5]` = 1500ms）
- 2 位 → 百分秒（`[00:01.50]` = 1500ms）**这是绝大多数 LRC 的写法**
- 3 位 → 毫秒（`[00:01.500]` = 1500ms）

把 2 位当毫秒处理是**最常见的实现错误**，症状是歌词整体慢 10 倍。

### 8.2 必须处理的边界

| 情况 | 处理 |
|---|---|
| 一行多个时间戳 | 每个时间戳各生成一行（同一句歌词重复出现） |
| `[ti:] [ar:] [al:] [by:]` 元信息行 | 跳过 |
| `[offset:+500] / [offset:-500]` | 整体时移：`t = t − offset`（**注意是减**，正数表示歌词提前） |
| 时间戳乱序（多时间戳必然导致） | 解析完统一按时间升序排序 |
| 空行 | 跳过 |

### 8.3 翻译合并

网易云把原文和翻译分成两段 LRC 返回。合并规则：

```dart
// 时间戳**完全相等**才配对；对不上的翻译行直接丢弃
final map = {for (final t in trans) t.t: t.s};
```

**宁可少显示一行翻译，也不要错位显示**。实践中翻译 LRC 的时间戳常常和原文
差几十到几百毫秒，做"最近邻匹配"会把翻译挂到错误的句子上，比不显示更糟。

### 8.4 当前行定位（二分）

```dart
int indexAt(List<LrcLine> lines, int posMs) {
  if (lines.isEmpty) return -1;
  if (posMs < lines.first.t) return -1;   // -1 = 前奏，还没到第一句
  // 二分查找最后一个 t <= posMs 的下标
}
```

**必须用二分**：这个函数在播放时要被高频调用（本实现每 100ms 一次），而歌词
可能有上百行。

## 9. 播放位置与绘制节流（渲染侧的配套）

歌词跟唱的关键是**位置要看起来连续**，但**采样不能太频繁**。

### 9.1 位置外推

```dart
var p = media['position'];                    // 播放器上次上报的位置
if (status == playing) {
  p += media['positionAge'];                  // 上报 → 我们采样之间的时间
  p += now - media['__localAt'];              // 采样 → 当前渲染之间的时间
}
```

- `positionAge` 由数据源给出（SMTC 有对应字段；没有就自己记）
- `__localAt` 是收到这份快照时的本地时间戳

**倒退保护**：只压制 2 秒以内的倒退（那是上报抖动），**大跳必须放行**——用户
拖动进度条就是大跳，拦掉会让进度条回不去。

```dart
if (_lastPos > 0 && p < _lastPos && _lastPos - p < 2000) p = _lastPos;
```

### 9.2 绘制指纹

只有**可见内容真的变了**才重绘：

```
指纹 = (当前行号, 秒数, 播放状态, 进度条像素位置)
```

进度条位置取整到像素（300px 宽上 1px 以内的变化不值得重绘）。这一条在桌面
常驻应用里很重要：歌词卡每秒重绘 60 次会让 GPU 一直有负载。

## 10. 移植清单

最小可用实现需要这些能力：

| # | 能力 | 备注 |
|---|---|---|
| 1 | 读系统媒体会话 | §1，平台相关，别的部分与平台无关 |
| 2 | HTTP GET + JSON | 需要能自定义 Header（网易云要 Referer） |
| 3 | JSON 序列化 | 缓存歌词用 |
| 4 | 持久化 KV 或文件 | §3，别放主配置 |
| 5 | 定时器（100ms 级）| 轮询播放状态；或改用事件回调 + 位置外推 |
| 6 | 能画带高亮的文本列表 | 渲染层 |

**建议的实现顺序**：

1. 先跑通**单一来源**（网易云：搜索 → 取词 → 解析 → 显示），不要一上来做多源
2. 加**缓存**（否则每次启动都联网，且切歌来回会重复请求）
3. 加**匹配打分**（这一步决定"搜到的第一首对不对"，是质量关键）
4. 再加**第二来源**（LRCLIB）当兜底
5. 最后补**兜底策略**（只搜歌手、标题变体）——这些是为跨语言/翻译名准备的

**验证方式**：拿这几类曲子各测一遍

- 中文流行（标题歌手都对得上）→ 应该直接命中
- 日文歌 + 英文元数据（如 `Golden Number` / `Iyowa` vs `黄金数` / `いよわ`）
  → 验证 §6 的权重是否生效
- 同一首歌的 live 版 / remix → 验证时长权重与垃圾词规则
- 冷门曲 → 验证"没找到"是否正常显示，而不是贴错词

## 11. 踩坑清单（按踩到的顺序）

1. **把 2 位小数当毫秒** → 歌词整体慢 10 倍。
2. **`get_current_session()` 拿到浏览器会话** → 读出来的是网页视频标题。要枚举
   全部会话再筛。
3. **歌手名跨文字匹配失败** → 收窄"歌手不匹配"的扣分，把权重交给时长。
4. **标题变体去重用了归一化字符串** → `X (Y)` 和 `X` 被当成同一变体，少试一路。
5. **翻译按时间戳最近邻匹配** → 翻译挂错句子。改成严格相等，对不上就丢。

7. **负缓存** → 网络恢复后仍显示"没找到"。搜不到不要写缓存。
8. **切歌间隙清空画面** → 闪白。加宽限期，保留到新歌词到位。
9. **进度条倒退保护拦掉了拖动** → 保护阈值要远小于"拖动跳变"的幅度。
10. **歌词塞进主配置文件** → 配置文件膨胀到不可维护。单独存。
